### Q1. Software Design and Its Process

`<sub>`{=html}**4 Marks** · **Knowledge** · **Cognitive Domain** ·
**CO1**`</sub>`{=html}

**Answer:**

Software design is a **problem-solving process**. In software
development, the requirements are the input to the design process. It
has two basic steps:

1.  **Architectural Design:** Also called high-level or top-level
    design. It describes how the software is organized into components.
2.  **Detailed Design:** It describes the desired behaviour of those
    components.

Therefore, architectural design defines the overall organization, while
detailed design explains the behaviour of individual components.

`<sub>`{=html}📖 Reference: `SoftEng-Design.pdf`, pages
3--6.`</sub>`{=html}

### Q2. Outcome and Design Rationale

`<sub>`{=html}**4 Marks** · **Understanding** · **Cognitive Domain** ·
**CO1**`</sub>`{=html}

**Answer:**

The outcome of the design process is a **set of models and artifacts**
that record the major decisions made during design, together with the
rationale for each nontrivial decision.

**Design rationale** is the explanation of why a particular design
decision was made. Recording it helps people understand the reasons
behind design decisions later. The slides state that recording rationale
enhances the **long-term maintainability** of the software product.

`<sub>`{=html}📖 Reference: `SoftEng-Design.pdf`, pages
7--8.`</sub>`{=html}

### Q3. Modularity, Coupling and Cohesion

`<sub>`{=html}**4 Marks** · **Knowledge** · **Cognitive Domain** ·
**CO2**`</sub>`{=html}

**Answer:**

-   **Modularity and Decomposition:** Dividing large software into
    smaller named components with well-defined interfaces that describe
    component interactions. Different functionalities and
    responsibilities are placed in different components.
-   **Coupling:** A measure of interdependence among components in a
    computer program. A good design aims for **low coupling**.
-   **Cohesion:** A measure of the strength of association among
    elements within a component. A good design aims for **high
    cohesion**.

> **Remember:** A good software design generally aims for **LOW
> COUPLING + HIGH COHESION**.

`<sub>`{=html}📖 Reference: `SoftEng-Design.pdf`, pages
9--13.`</sub>`{=html}

### Q4. Abstraction, Encapsulation and Information Hiding

`<sub>`{=html}**4 Marks** · **Understanding** · **Cognitive Domain** ·
**CO2**`</sub>`{=html}

**Answer:**

-   **Abstraction:** A view of an object that focuses on information
    relevant to a particular purpose and ignores the remaining
    information.
-   **Encapsulation:** Grouping and packaging the internal details of an
    abstraction.
-   **Information Hiding:** Making those internal details inaccessible
    to external entities.

Encapsulation and information hiding package the internal details and
prevent external entities from directly accessing them. This separates
the externally visible view from internal implementation details.

`<sub>`{=html}📖 Reference: `SoftEng-Design.pdf`, page
14.`</sub>`{=html}

### Q5. CBO, LCOM and WMC

`<sub>`{=html}**8 Marks** · **Understanding** · **Cognitive Domain** ·
**CO3**`</sub>`{=html}

**Answer:**

Software design quality can be assessed through **software design
reviews** and **software metrics**. Reviews may use informal or formal
techniques to examine design artifacts, while metrics quantify the
assessment. The slides identify the **Chidamber and Kemerer (CK) metrics
suite** as a well-known set for object-oriented software.

#### 1. Coupling Between Object Classes (CBO)

CBO measures the number of classes used by a particular class.

``` text
CBO(A) = number of classes used by A
```

Inheritance is typically not counted. In the slide example, `Controller`
uses `Bell` and `Light`; therefore:

``` text
CBO(Controller) = 2
```

#### 2. Lack of Cohesion of Methods (LCOM)

LCOM measures lack of cohesion among the methods of a class.

-   **Q set:** Pairs of class methods that use common attributes.
-   **P set:** Pairs of class methods that do not use common attributes.

The slide formula is:

``` text
LCOM(x) = |P| − |Q|, if |P| > |Q|
LCOM(x) = 0,       if |P| ≤ |Q|
```

In the Rectangle example, `Q = 3` and `P = 0`, so `LCOM = 0`.

The slides also introduce:

``` text
LCOM2(x) = 1 − Sum(mai)/(m × a)
```

Where:

-   `m` = number of methods
-   `a` = number of attributes
-   `mai` = number of methods that use attribute `ai`

The slides state that a **smaller LCOM2 value is better**.

#### 3. Weighted Methods per Class (WMC)

WMC measures class complexity by adding the complexity of its methods.

``` text
WMC(A) = Sum(Ci), i = 1 to N methods
```

Here, `Ci` is the complexity of method `i`. The slides mention:

-   **Lines of Code (LOC)**
-   **McCabe complexity**, calculated as the number of conditions plus
    1.

The slides count `if`, `for` and `while` as one condition each. In the
Controller example, the McCabe version of WMC is shown as `10`.

#### Quick Revision

  Metric     What it measures
  ---------- -------------------------------------------
  **CBO**    Number of classes used by a class
  **LCOM**   Lack of cohesion among class methods
  **WMC**    Weighted complexity of methods in a class

`<sub>`{=html}📖 Reference: `SoftEng-Design.pdf`, pages
15--29.`</sub>`{=html}

### Q6. Software Architecture and Architectural Styles

`<sub>`{=html}**4 Marks** · **Knowledge** · **Cognitive Domain** ·
**CO4**`</sub>`{=html}

**Answer:**

In its strict sense, **software architecture** is the set of structures
needed to reason about a system. These structures comprise software
elements, relations among them, and properties of both.

Two architectural styles are:

**1. Layered Architecture**

Components are organized in layers. Each layer depends only on the next
layer, as described in the slides.

**2. Event-Based Architecture**

It contains event producers and consumers. Producers generate events,
and consumers receive or consume them through an event-distribution
mechanism. Consumers can register for events.

`<sub>`{=html}📖 Reference: `SoftEng-Design.pdf`, pages
30--36.`</sub>`{=html}

### Q7. Model--View--Controller (MVC) Architectural Style

`<sub>`{=html}**4 Marks** · **Understanding** · **Cognitive Domain** ·
**CO4**`</sub>`{=html}

**Answer:**

**Model--View--Controller (MVC)** is an architectural style with three
components:

1.  **Model:** Represents information about the domain.
2.  **View:** Represents the display of the model in the user interface
    (UI).
3.  **Controller:** Takes user input, manipulates the model, and causes
    the view to update appropriately.

In MVC, the UI is a combination of the **View** and the **Controller**.
The Model holds domain information, the View displays it, and the
Controller handles input and coordinates updates.

`<sub>`{=html}📖 Reference: `SoftEng-Design.pdf`, page
37.`</sub>`{=html}

### Q8. Strategy and Adapter Design Patterns

`<sub>`{=html}**8 Marks** · **Understanding** · **Cognitive Domain** ·
**CO5**`</sub>`{=html}

**Answer:**

#### A. Strategy Design Pattern

**Intent:** Defines a family of algorithms, encapsulates each one, and
makes them interchangeable. It lets an algorithm vary independently from
clients that use it.

**Structure:**

-   **Strategy:** Declares a common interface for supported algorithms.
-   **ConcreteStrategy:** Implements an algorithm using the Strategy
    interface. The slides give `WalkingStrategy` and `CarStrategy` as
    examples.
-   **Context:** Maintains a reference to a Strategy object and uses the
    interface to call the selected algorithm. The slide example uses
    `Navigator` as Context.

**Benefits:**

-   Isolates Context from algorithm implementation details.
-   New strategies can be added without changing Context.
-   Avoids complex conditionals for alternative algorithms in Context.
-   Algorithms can be swapped at runtime.

**Liabilities:**

-   A common interface for different algorithms may be difficult to
    specify.
-   Strategies increase the number of objects in an application.

#### B. Adapter Design Pattern

**Intent:** Converts the interface of a class into another interface
expected by clients. It allows classes to work together when they
otherwise could not because their interfaces are incompatible.

**Structure:**

-   **Target:** Defines the domain-specific interface used by the Client
    (`Shape` in the slide example).
-   **Client:** Collaborates with objects conforming to the Target
    interface (`DrawingEditor`).
-   **Adaptee:** Defines an existing interface that needs adapting
    (`TextView`).
-   **Adapter:** Adapts the Adaptee interface to the Target interface
    (`TextShape`).

**Benefit:**

-   Adaptees can be added or used without changing existing code.

**Liability:**

-   Overall code complexity increases because new classes and a level of
    indirection are introduced.

`<sub>`{=html}📖 Reference: `SoftEng-Design.pdf`, pages 40--43 and
47--62.`</sub>`{=html}
